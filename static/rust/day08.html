1. 从 Option<T> 到 Result<T, E>

Day 7 学过：

#![allow(unused)]
fn main() {
enum Option<T> {
    Some(T),
    None,
}
}

Option<T> 表达：

有值 / 没有值

例如：

#![allow(unused)]
fn main() {
fn find_even(nums: &[i32]) -> Option<i32> {
    for n in nums {
        if *n % 2 == 0 {
            return Some(*n);
        }
    }

    None
}
}

但是 Option<T> 只能表达“没有”，不能表达“为什么没有”。

Result<T, E> 用来表达：

成功 / 失败，并且失败时带有原因

它大致可以理解为：

#![allow(unused)]
fn main() {
enum Result<T, E> {
    Ok(T),
    Err(E),
}
}

含义：

形式含义
Ok(T)成功，并携带成功结果
Err(E)失败，并携带错误原因

例如：

#![allow(unused)]
fn main() {
Result<i32, String>
}

可以读作：

要么成功得到 i32，要么失败得到 String 错误信息。

2. 最简单的 Result：安全除法

完整示例：

fn divide(a: i32, b: i32) -> Result<i32, String> {
    if b == 0 {
        Err(String::from("cannot divide by zero"))
    } else {
        Ok(a / b)
    }
}

fn main() {
    for (a, b) in [(10, 2), (10, 0)] {
        match divide(a, b) {
            Ok(value) => println!("{a} / {b} = {value}"),
            Err(message) => println!("failed to divide {a} by {b}: {message}"),
        }
    }
}

输出：

10 / 2 = 5
failed to divide 10 by 0: cannot divide by zero

这里：

#![allow(unused)]
fn main() {
fn divide(a: i32, b: i32) -> Result<i32, String>
}

表示：

如果除法合法，返回 Ok(i32)。
如果 b == 0，返回 Err(String)。

调用处用 match 分别处理成功和失败：

#![allow(unused)]
fn main() {
match divide(a, b) {
    Ok(value) => println!("{a} / {b} = {value}"),
    Err(message) => println!("failed to divide {a} by {b}: {message}"),
}
}

这和 Option<T> 的模式很像：

match value {
    Some(x) => ...,
    None => ...,
}

只不过 Result<T, E> 的失败分支会携带错误信息。

3. 文件读取天然返回 Result

Rust 标准库中的文件读取函数：

#![allow(unused)]
fn main() {
std::fs::read_to_string(path)
}

返回类型是：

#![allow(unused)]
fn main() {
Result<String, std::io::Error>
}

因为文件读取可能失败，例如：

  • 文件不存在
  • 路径是目录
  • 没有读取权限
  • 文件系统出错

所以 Rust 不会让你假装文件读取一定成功，而是把“可能失败”写进类型。

手动处理文件读取错误：

use std::fs;
use std::io;

fn read_username_manual(path: &str) -> Result<String, io::Error> {
    let content_result = fs::read_to_string(path);

    match content_result {
        Ok(content) => Ok(content.trim().to_string()),
        Err(error) => Err(error),
    }
}

fn main() {
    match read_username_manual("username.txt") {
        Ok(name) => println!("username = {name}"),
        Err(error) => println!("failed to read username: {error}"),
    }
}

这里：

#![allow(unused)]
fn main() {
fs::read_to_string(path)
}

得到的是：

#![allow(unused)]
fn main() {
Result<String, io::Error>
}

如果成功，content 是文件内容；如果失败，error 是具体的 I/O 错误。

4. ? 运算符：传播错误

手动 match 很常见，所以 Rust 提供了 ? 简化错误传播。

下面两个函数语义相同。

手动版本：

#![allow(unused)]
fn main() {
use std::fs;
use std::io;

fn read_username_manual(path: &str) -> Result<String, io::Error> {
    let content_result = fs::read_to_string(path);

    match content_result {
        Ok(content) => Ok(content.trim().to_string()),
        Err(error) => Err(error),
    }
}
}

? 版本：

#![allow(unused)]
fn main() {
use std::fs;
use std::io;

fn read_username_question_mark(path: &str) -> Result<String, io::Error> {
    let content = fs::read_to_string(path)?;
    Ok(content.trim().to_string())
}
}

这一行：

#![allow(unused)]
fn main() {
let content = fs::read_to_string(path)?;
}

可以理解为：

let content = match fs::read_to_string(path) {
    Ok(value) => value,
    Err(error) => return Err(error),
};

也就是说：

如果是 Ok(value)，? 取出 value，程序继续执行。
如果是 Err(error)，? 立刻从当前函数返回 Err(error)。

? 不是忽略错误，而是把错误向上传播。

5. ? 对函数签名的要求

如果在函数内部写：

#![allow(unused)]
fn main() {
fs::read_to_string(path)?
}

那么当前函数也必须能返回相应的错误。

例如下面是合法的：

#![allow(unused)]
fn main() {
use std::fs;
use std::io;

fn read_username(path: &str) -> Result<String, io::Error> {
    let content = fs::read_to_string(path)?;
    Ok(content.trim().to_string())
}
}

因为当前函数返回：

#![allow(unused)]
fn main() {
Result<String, io::Error>
}

如果文件读取失败，? 可以直接返回：

#![allow(unused)]
fn main() {
Err(io::Error)
}

但如果函数写成：

fn read_username(path: &str) -> String {
    let content = fs::read_to_string(path)?;
    content.trim().to_string()
}

就不合理，因为失败时不知道应该返回什么 String。

当前阶段可以先记住：

想用 ? 传播 Result 错误，函数自己通常也要返回 Result。

6. .trim()：清理字符串两端空白

读取文本文件时经常会看到：

#![allow(unused)]
fn main() {
content.trim()
}

.trim() 会去掉字符串开头和结尾的空白字符，包括：

  • 空格
  • 换行 \n
  • 制表符 \t
  • Windows 换行里的 \r\n

例如：

fn main() {
    let text = "  42\n";
    let cleaned = text.trim();

    println!("before = {:?}", text);
    println!("after  = {:?}", cleaned);
}

输出：

before = "  42\n"
after  = "42"

它不会删除字符串中间的空格：

fn main() {
    let text = "  hello rust  ";
    println!("{:?}", text.trim());
}

输出：

"hello rust"

中间的空格仍然存在。

.trim() 不会原地修改原字符串，而是返回一个 &str 视图：

fn main() {
    let text = String::from("  hello  ");
    let cleaned = text.trim();

    println!("text = {:?}", text);
    println!("cleaned = {:?}", cleaned);
}

输出：

text = "  hello  "
cleaned = "hello"

所以在下面这个函数里：

#![allow(unused)]
fn main() {
use std::fs;
use std::io;

fn read_username(path: &str) -> Result<String, io::Error> {
    let content = fs::read_to_string(path)?;
    Ok(content.trim().to_string())
}
}

流程是：

String -> trim 得到 &str -> to_string 得到新的 String

因为函数返回类型要求是：

#![allow(unused)]
fn main() {
Result<String, io::Error>
}

所以最后需要 .to_string()。

7. 解析数字：parse::<i32>()

字符串解析为数字也可能失败。

例如：

use std::num::ParseIntError;

fn parse_number(text: &str) -> Result<i32, ParseIntError> {
    let number = text.trim().parse::<i32>()?;
    Ok(number)
}

fn main() {
    match parse_number("123") {
        Ok(n) => println!("parsed number = {n}"),
        Err(error) => println!("parse error: {error}"),
    }

    match parse_number("abc") {
        Ok(n) => println!("parsed number = {n}"),
        Err(error) => println!("parse error: {error}"),
    }
}

输出：

parsed number = 123
parse error: invalid digit found in string

这里：

#![allow(unused)]
fn main() {
text.trim().parse::<i32>()
}

返回：

#![allow(unused)]
fn main() {
Result<i32, ParseIntError>
}

因为：

"123" 可以解析成 i32
"abc" 不能解析成 i32

8. 一个函数里有多种错误：Box<dyn Error>

有些函数可能在多个步骤失败。

例如：

  1. 读取文件，可能产生 io::Error
  2. 解析数字，可能产生 ParseIntError

可以先使用：

#![allow(unused)]
fn main() {
Box<dyn std::error::Error>
}

作为通用错误类型。

完整示例：

use std::fs;

fn read_number(path: &str) -> Result<i32, Box<dyn std::error::Error>> {
    let content = fs::read_to_string(path)?;
    let number = content.trim().parse::<i32>()?;
    Ok(number)
}

fn main() {
    match read_number("number.txt") {
        Ok(n) => println!("number from file = {n}"),
        Err(error) => println!("failed to read number: {error}"),
    }
}

当前阶段可以把：

#![allow(unused)]
fn main() {
Box<dyn std::error::Error>
}

理解成：

能装下多种错误类型的通用错误盒子。

以后学习 trait、动态分发、错误类型设计时，会再深入理解它。

9. main 也可以返回 Result

普通写法：

fn main() {
    println!("hello");
}

如果想在 main 中使用 ?，可以让 main 返回 Result：

use std::fs;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    fs::write("number.txt", "42\n")?;
    let content = fs::read_to_string("number.txt")?;

    println!("content = {}", content.trim());

    Ok(())
}

这里：

#![allow(unused)]
fn main() {
Result<(), Box<dyn std::error::Error>>
}

表示：

成功时没有有意义的返回值：()
失败时返回某种错误。

最后的：

#![allow(unused)]
fn main() {
Ok(())
}

表示程序正常结束。

10. match、?、unwrap()、expect() 的区别

假设有：

#![allow(unused)]
fn main() {
let result = std::fs::read_to_string("number.txt");
}

它的类型是：

#![allow(unused)]
fn main() {
Result<String, std::io::Error>
}

常见处理方式有四种。

10.1 match：显式处理

#![allow(unused)]
fn main() {
match std::fs::read_to_string("number.txt") {
    Ok(content) => println!("content = {}", content),
    Err(error) => println!("failed to read file: {}", error),
}
}

特点：

成功怎么处理，失败怎么处理，都写清楚。

适合在程序边界层处理错误，例如 main、CLI、用户界面。

10.2 ?：向上传播

let content = std::fs::read_to_string("number.txt")?;

特点：

当前函数不处理错误，而是交给调用者。

适合中间函数。

10.3 unwrap()：失败就 panic

#![allow(unused)]
fn main() {
let content = std::fs::read_to_string("number.txt").unwrap();
}

含义：

如果是 Ok(value)，取出 value。
如果是 Err(error)，程序 panic。

适合快速实验或测试代码，不适合正式处理用户输入、文件、网络等外部失败。

10.4 expect()：失败就 panic，但带说明

#![allow(unused)]
fn main() {
let content = std::fs::read_to_string("number.txt")
    .expect("number.txt should exist for this demo");
}

expect() 和 unwrap() 类似，也会在失败时 panic，但它可以提供更清晰的上下文信息。

正式代码中如果确实要 panic，通常 expect() 比裸 unwrap() 更好。

11. Err 不是 panic

这是一个重要区别。

#![allow(unused)]
fn main() {
Err(error)
}

只是一个普通值，表示操作失败了，但程序还可以继续运行。

例如：

fn divide(a: i32, b: i32) -> Result<i32, String> {
    if b == 0 {
        Err(String::from("cannot divide by zero"))
    } else {
        Ok(a / b)
    }
}

fn main() {
    match divide(10, 0) {
        Ok(n) => println!("result = {n}"),
        Err(error) => println!("error: {error}"),
    }

    println!("program is still running");
}

输出：

error: cannot divide by zero
program is still running

而：

divide(10, 0).unwrap();

会把 Err 变成 panic。

所以：

Result 是可恢复错误。
panic 是不可恢复崩溃。

12. 多行文件解析：lines()、enumerate() 与 map_err

今天的主实验读取一个多行数字文件，解析成 Vec<i32>，并在错误中报告行号。

完整示例：

use std::fs;

fn parse_numbers_from_text(text: &str) -> Result<Vec<i32>, String> {
    let mut numbers = Vec::new();

    for (index, line) in text.lines().enumerate() {
        let trimmed = line.trim();

        if trimmed.is_empty() {
            continue;
        }

        let number = trimmed.parse::<i32>().map_err(|error| {
            format!(
                "line {}: cannot parse {:?}: {}",
                index + 1,
                trimmed,
                error
            )
        })?;

        numbers.push(number);
    }

    Ok(numbers)
}

fn read_numbers(path: &str) -> Result<Vec<i32>, Box<dyn std::error::Error>> {
    let content = fs::read_to_string(path)?;
    let numbers = parse_numbers_from_text(&content)?;
    Ok(numbers)
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    fs::write("numbers.txt", "10\n20\n\n30\n")?;
    fs::write("bad_numbers.txt", "10\nabc\n30\n")?;

    match read_numbers("numbers.txt") {
        Ok(numbers) => {
            let total: i32 = numbers.iter().sum();
            println!("numbers = {:?}", numbers);
            println!("total = {total}");
        }
        Err(error) => println!("failed to read numbers: {error}"),
    }

    match read_numbers("bad_numbers.txt") {
        Ok(numbers) => println!("numbers = {:?}", numbers),
        Err(error) => println!("failed to read numbers: {error}"),
    }

    Ok(())
}

输出：

numbers = [10, 20, 30]
total = 60
failed to read numbers: line 2: cannot parse "abc": invalid digit found in string

12.1 lines()

#![allow(unused)]
fn main() {
text.lines()
}

会把字符串按行切开。

例如：

fn main() {
    let text = "10\n20\n30\n";

    for line in text.lines() {
        println!("line = {:?}", line);
    }
}

输出：

line = "10"
line = "20"
line = "30"

每一行的类型是 &str。

12.2 enumerate()

#![allow(unused)]
fn main() {
text.lines().enumerate()
}

会给每个元素加上编号：

fn main() {
    let text = "10\n20\n30\n";

    for (index, line) in text.lines().enumerate() {
        println!("index = {index}, line = {line}");
    }
}

输出：

index = 0, line = 10
index = 1, line = 20
index = 2, line = 30

因为程序员习惯从 0 开始计数，而用户习惯从 1 开始看行号，所以错误信息中通常写：

#![allow(unused)]
fn main() {
index + 1
}

12.3 continue

#![allow(unused)]
fn main() {
if trimmed.is_empty() {
    continue;
}
}

表示：

如果这一行清理后是空字符串，就跳过本轮循环，继续处理下一行。

所以：

10
20

30

中间的空行不会导致解析失败。

12.4 map_err

这一行是错误上下文的关键：

#![allow(unused)]
fn main() {
let number = trimmed.parse::<i32>().map_err(|error| {
    format!(
        "line {}: cannot parse {:?}: {}",
        index + 1,
        trimmed,
        error
    )
})?;
}

trimmed.parse::<i32>() 的类型是：

#![allow(unused)]
fn main() {
Result<i32, ParseIntError>
}

但 parse_numbers_from_text 返回：

#![allow(unused)]
fn main() {
Result<Vec<i32>, String>
}

所以需要把错误类型从 ParseIntError 转成 String。

map_err 的作用是：

如果是 Ok(value)，保持 Ok(value) 不变。
如果是 Err(error)，把 error 转换成另一个错误。

也就是：

Result<i32, ParseIntError>
    -> map_err(...)
Result<i32, String>

然后最后的 ?：

Ok(number)  -> 取出 number，继续执行
Err(String) -> 立刻返回 Err(String)

这样错误信息就能从：

invalid digit found in string

增强为：

line 2: cannot parse "abc": invalid digit found in string

这在真实工程里非常重要，因为好的错误信息应该回答：

哪里错了？哪个输入错了？为什么错了？

13. 什么时候用 Result，什么时候用 panic

Rust 通常把错误分为两类。

13.1 可恢复错误：用 Result

如果失败是正常可能发生的，程序应该有机会处理，就用 Result。

例如：

  • 用户输入了非法数字
  • 文件不存在
  • 网络请求失败
  • 配置文件格式不对
  • 权限不足
  • 某一行文本解析失败

这些不是程序员写错代码，而是外部世界本来就可能这样。

例如：

#![allow(unused)]
fn main() {
fn read_number(path: &str) -> Result<i32, Box<dyn std::error::Error>> {
    let content = std::fs::read_to_string(path)?;
    let number = content.trim().parse::<i32>()?;
    Ok(number)
}
}

13.2 不可恢复错误：可以 panic

如果某个错误发生时说明程序内部逻辑已经坏了，继续运行没有意义，可以用 panic。

例如：

  • 数组越界访问
  • 违反程序内部不变量
  • 某个理论上绝不应该发生的分支真的发生了
  • 测试中发现结果不符合预期

“不变量”指的是：

程序在某个位置必须始终满足的条件。

例如下面这个函数假设输入切片非空：

#![allow(unused)]
fn main() {
fn average(nums: &[i32]) -> f64 {
    if nums.is_empty() {
        panic!("nums should not be empty");
    }

    let sum: i32 = nums.iter().sum();
    sum as f64 / nums.len() as f64
}
}

如果调用者传入空切片，就违反了函数约定。

不过更安全的 API 往往会用 Option 或 Result 表达这种可能性：

#![allow(unused)]
fn main() {
fn average(nums: &[i32]) -> Option<f64> {
    if nums.is_empty() {
        return None;
    }

    let sum: i32 = nums.iter().sum();
    Some(sum as f64 / nums.len() as f64)
}
}

这里用 Option<f64> 很合适，因为失败原因只有一种：没有数字，无法计算平均值。

14. Result、Option、panic 的选择

可以用下面的表判断：

场景推荐
可能没有值，但没有复杂错误原因Option<T>
可能失败，而且需要说明失败原因Result<T, E>
外部输入、文件、网络、解析Result<T, E>
程序内部逻辑不变量被破坏panic!
快速实验可以临时用 unwrap()
测试代码unwrap() / expect() 常见
正式代码中确信不会失败优先 expect("说明为什么不该失败")，少用裸 unwrap()

实用原则：

能恢复，用 Result。
可能没有，用 Option。
程序员 bug，用 panic。
实验代码可以 unwrap。
正式代码少 unwrap，多用 ?、match、expect。

更工程化一点：

在函数内部用 ? 传播错误；
在边界层用 match 展示错误；
在错误发生处用 map_err / 自定义错误增加上下文；
只有不可恢复的逻辑错误才 panic。

15. Library 和 Application 的区别

如果你在写库代码，也就是别人会调用你的函数，通常应该少 panic，多返回 Result。

库代码更推荐：

fn load_config(path: &str) -> Result<Config, ConfigError> {
    // ...
}

而不是：

fn load_config(path: &str) -> Config {
    // ...
    panic!("failed to load config");
}

因为库不应该随便替调用者决定：

程序必须崩溃。

应用程序的最外层可以决定如何展示错误、是否退出程序：

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = load_config("config.toml")?;
    run(config)?;
    Ok(())
}

或者：

fn main() {
    match run() {
        Ok(()) => {}
        Err(error) => {
            eprintln!("error: {}", error);
            std::process::exit(1);
        }
    }
}

常见风格是：

底层函数返回 Result。
顶层函数决定如何展示错误、是否退出程序。

use std::fs;

fn parse_scores_from_text(text: &str) -> Result<Vec<f64>, String> {
    let mut scores = Vec::new();

    for (index, line) in text.lines().enumerate() {
        let trimmed = line.trim();

        if trimmed.is_empty() {
            continue;

        let score = trimmed.parse::<f64>().map_err(|error| {
            format!(

                index + 1,
                trimmed,
                error
            )
        })?;

        scores.push(score);
    }

    Ok(scores)
}

fn average(scores: &[f64]) -> Option<f64> {
    if scores.is_empty() {
        return None;
    }

    let total: f64 = scores.iter().sum();
    Some(total / scores.len() as f64)
}

fn read_scores(path: &str) -> Result<Vec<f64>, Box<dyn std::error::Error>> {
    let content = fs::read_to_string(path)?;
    let scores = parse_scores_from_text(&content)?;
    Ok(scores)
}

            None => println!("no scores"),
        },
        Err(error) => println!("failed to read scores: {error}"),
    }

}

17.1 Ok(scores) 的作用

这个函数签名是：

#![allow(unused)]
fn main() {
fn parse_scores_from_text(text: &str) -> Result<Vec<f64>, String>
}

它不是返回：

#![allow(unused)]
fn main() {
Vec<f64>
}

而是返回：

#![allow(unused)]
fn main() {
Result<Vec<f64>, String>
}

所以函数最后不能直接写：

scores

因为 scores 的类型只是：

#![allow(unused)]
fn main() {
Vec<f64>
}

必须写：

#![allow(unused)]
fn main() {
Ok(scores)
}

这表示：

成功解析出了 Vec<f64>，现在把它包装成 Result 的成功分支返回。

类型关系是：

scores: Vec<f64>
Ok(scores): Result<Vec<f64>, String>

同理，如果失败，则返回：

#![allow(unused)]
fn main() {
Err(message)
}

其中：

message: String
Err(message): Result<Vec<f64>, String>

17.2 Ok 的两个位置：构造与匹配

同样写作 Ok(scores)，在不同位置含义不同。

在函数返回处：

#![allow(unused)]
fn main() {
Ok(scores)
}

表示“构造一个成功的 Result 值”。

在 match 中：

#![allow(unused)]
fn main() {
match read_scores("scores.txt") {
    Ok(scores) => println!("{:?}", scores),
    Err(error) => println!("{error}"),
}
}

这里的 Ok(scores) 表示“匹配成功分支，并把里面的值取出来命名为 scores”。

位置含义
函数最后 Ok(scores)构造成功结果
match 里的 Ok(scores) => ...匹配成功结果并拆包

Some(value) 也有同样的两种用法。

17.3 ?：从 Result 里取值，或提前返回错误

这一行：

#![allow(unused)]
fn main() {
let score = trimmed.parse::<f64>().map_err(|error| {
    format!(
        "line {}: cannot parse {:?}: {}",
        index + 1,
        trimmed,
        error
    )
})?;
}

类型流动如下：

trimmed: &str
trimmed.parse::<f64>(): Result<f64, ParseFloatError>
map_err(...): Result<f64, String>
?: 成功时取出 f64，失败时提前返回 Err(String)
score: f64

也就是说，? 的作用是：

如果是 Ok(value)，取出 value，赋给 score。
如果是 Err(error)，立刻从 parse_scores_from_text 返回 Err(error)。

所以 ? 不是忽略错误，而是把错误沿着函数返回类型传播出去。

17.4 写变量类型时的判断方法

Rust 有类型推断，不是所有变量都需要手动标类型。但初学阶段可以主动标出关键类型，帮助自己建立类型感。

例如：

#![allow(unused)]
fn main() {
let mut scores: Vec<f64> = Vec::new();
}

表示 scores 是一个装 f64 的动态数组。

#![allow(unused)]
fn main() {
let score: f64 = trimmed.parse::<f64>().map_err(|error| {
    format!("line {}: cannot parse {:?}: {}", index + 1, trimmed, error)
})?;
}

表示这一行最终成功时得到的是一个 f64。

#![allow(unused)]
fn main() {
let total: f64 = scores.iter().sum();
}

这里建议标注 f64，因为 sum() 是泛型方法，类型提示能让代码更清楚。

一个实用原则：

能从右边明显看出来的，可以省略类型。
Vec::new()、parse、sum 这类容易让人迷糊的地方，初学时可以多写类型。

判断是否为空：

求和：

整数转浮点数：

#![allow(unused)]

scores.len() as f64
}

字符串解析浮点数：

17.6 返回值小抄

如果函数签名是：

#![allow(unused)]
fn main() {
fn f() -> Result<T, E>
}

成功返回：

#![allow(unused)]
fn main() {
Ok(value_of_type_T)
}

失败返回：

#![allow(unused)]
fn main() {
Err(error_of_type_E)
}

如果函数签名是：

#![allow(unused)]
fn main() {
fn f() -> Option<T>
}

有值返回：

#![allow(unused)]
fn main() {
Some(value_of_type_T)
}

没值返回：

#![allow(unused)]
fn main() {
None
}

所以：

#![allow(unused)]
fn main() {
fn average(scores: &[f64]) -> Option<f64> {
    if scores.is_empty() {
        return None;
    }

    let total: f64 = scores.iter().sum();
    Some(total / scores.len() as f64)
}
}

这里：

None: Option<f64>
Some(...): Option<f64>

它们都和函数签名一致。

17.7 本次练习暴露出的核心问题

这次练习中，最容易卡住的不是算法，而是 Rust 的“类型包装”意识：

Vec<f64> 要用 Ok(...) 包成 Result<Vec<f64>, String>。
f64 要从 Result<f64, String> 里用 ? 取出来。
平均值 f64 要用 Some(...) 包成 Option<f64>。
没有平均值时返回 None。

以后写 Rust 函数时，可以先问自己四个问题：

1. 函数签名说最终返回什么类型？
2. 成功值是什么类型？
3. 失败值是什么类型？
4. 当前这一步拿到的是普通值，还是 Result / Option 包装值？

这比一开始就直接敲代码更稳。

今日总结

Day 8 的核心地图：

概念关键点
Result<T, E>表达成功或失败
Ok(T)成功，并携带结果
Err(E)失败，并携带错误信息
match显式处理成功和失败
?成功则取值，失败则提前返回
std::fs::read_to_string读取文件，返回 Result<String, io::Error>
.trim()去掉字符串两端空白，常用于清理换行
.parse::<i32>()字符串解析数字，返回 Result<i32, ParseIntError>
Box<dyn Error>当前阶段可理解为通用错误盒子
unwrap()成功取值，失败 panic
expect()成功取值，失败 panic，但带自定义说明
map_err转换错误类型，常用于增加上下文
panic!表示不可恢复错误或程序内部不变量被破坏

一句话总结：

Rust 不把普通失败藏起来，而是用 Result 把失败写进类型，让调用者必须面对。
